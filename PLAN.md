# Plan: Duet v1 — scaffold, security rules, Google auth + couple pairing, CallService stub
Goal: Ship a Flutter+Firebase skeleton where two users sign in with Google, pair via a 6-digit invite code (Cloud Function, emulator-tested), guarded by tested Firestore rules, with all call logic behind CallService.
Assumptions:
- Repo is empty (only .git/.claude); no real Firebase project yet — config files use placeholder IDs (`duet-dev`) and firebase_options.dart placeholders; everything must run against emulators only.
- Flutter SDK >=3.22 / Dart >=3.4 available to builders; Node 20 for functions.
- Pairing decision: all pairing writes go through callable Cloud Functions (Admin SDK, transactions): `createInvite`, `redeemInvite`, `unpair`. Clients never write couples docs or users.coupleId; rules enforce this. Invite code: 6 random digits, uniqueness checked by querying `couples` where inviteCode==code; stored on couple doc with `inviteCodeExpiresAt` (now+24h). Pending couple = memberUids:[creator]; redeem transaction verifies code match, not expired, couple has 1 member, redeemer's coupleId is null, then sets memberUids to both, deletes inviteCode/inviteCodeExpiresAt, sets both users' coupleId. `unpair` deletes the couple doc and clears both users' coupleId (subcollection purge best-effort, untested).
- Prompt unlock decision: rules allow prompt create only with unlockedAt==null and content read only by author or when unlockedAt!=null; clients can never set/modify unlockedAt (Cloud Function unlock trigger is a later feature).

## Acceptance criteria
A1. `flutter analyze` exits 0; pubspec.yaml dependencies are exactly a subset of the 7 allowed packages (dev_dependencies excluded).
A2. `npm --prefix functions test` (emulators:exec) exits 0 with all pairing and rules tests passing; both test files exist and cover every case listed in S9/S10.
A3. Grep proof of abstraction: `meet_link_call_service.dart` is imported only by lib/services/call/call_service_locator.dart; no file outside lib/services/call/ references "Meet" or meet URLs.
A4. firestore.rules: emulator tests demonstrate a third UID cannot read or write any couples/{id} doc or subdocument, memberUids is never client-writable, and prompt content is invisible to the non-author until unlockedAt is non-null.
A5. Every user-visible string literal in lib/screens/ and lib/app.dart comes from AppStrings (grep for quoted literals inside Text(...) in screens returns none).
A6. app_theme.dart defines both light and dark ThemeData from the 0xFFB4574E seed; MaterialApp sets theme, darkTheme, and themeMode.
A7. CallService abstract class matches the mandated signature verbatim; MeetLinkCallService compiles but throws UnimplementedError.
A8. Full pairing flow works against emulators: createInvite returns a 6-digit code stored on a pending couple doc; redeemInvite by a second UID results in both users/{uid}.coupleId set and inviteCode fields removed.

## Out of scope
- Actual Meet link generation, url_launcher call flow, and the calls subcollection lifecycle (interface + stub only).
- Moods, prompts UI, prompt-unlock Cloud Function trigger, movie nights (rules cover their subcollections; no client features).
- Hindi localization (strings centralized only), real Firebase project provisioning, CI setup, push notifications, subcollection purge on unpair.
